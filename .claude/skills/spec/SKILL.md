# /spec — 要件インタビューと設計書の作成

## 1. 準備

- CLAUDE.md と docs/adr/ を読み、決まっている方針を把握する
- 既存の docs/specs/ を確認し、次の番号（NNN）を決める
- 入力としてヒアリングメモ（例: docs/specs/NNN-*/INTERVIEW.md）があれば読む

## 2. インタビュー

- まだ決まっていない論点を AskUserQuestion の選択式で聞く。1 回に最大 4 問、推奨案を先頭に置き「(Recommended)」と付ける
- 必ず確認する観点:
  - 画面と操作（スマホ前提。Android Chrome と iOS Safari）
  - 入力項目・必須/任意・検証ルール
  - 例外ケース（空・重複・期限切れ・削除/処分済み）
  - 権限（世帯内の 2 人の扱い）と個人情報の扱い
  - スコープ外にするもの
- 答えが仕様として矛盾なくまとまるまで続ける。ADR と食い違う要望が出たら、その場で指摘する

## 3. 設計書の作成

`docs/specs/NNN-機能名/` に次の 2 つを作る。

### SPEC.md（目安 150 行以内）

1. 目的とスコープ（含む / 含まない）
2. 用語
3. データモデル（テーブル・項目・型・必須・制約。全テーブルに世帯 ID）
4. 画面一覧と画面ごとの操作
5. 業務ルール（計算方法・状態遷移・通知条件）
6. セキュリティ・個人情報（CLAUDE.md のルールへの対応）
7. **受け入れ条件**: verify で E2E として確認できる形で書く（「〜すると〜が表示される」）
8. 実装の分割（PR 単位。1 PR は小さく）
9. 未決事項
10. 新しい ADR の候補（あれば docs/adr/ に「状態: 提案」で下書きを作る）

### design.html（1 ファイルで完結する HTML）

- スマホ幅の画面モック（主要画面すべて）
- データフロー図（入力 → サーバー関数 → データアクセス層 → D1/R2）
- レビューしてほしいコード断片（データアクセス関数のシグネチャなど）
- 外部の CSS・JS・フォントは読み込まない

## 4. 完了

- ユーザーに SPEC.md と design.html の場所、未決事項、ADR 候補を伝え、レビューを依頼する
- **承認されるまで実装を始めない**
