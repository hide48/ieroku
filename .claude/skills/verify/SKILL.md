# /verify — 変更の検証と証拠の作成

## 1. 静的チェック

1. `pnpm check`（lint・format・型チェック）を実行し、エラーを 0 にする
2. `pnpm test`（単体テスト）を実行する
   - 権限まわりを変更した場合、「他の世帯のデータにアクセスできない」テストが含まれていることを確認する

## 2. 起動と E2E

1. `pnpm db:seed` でダミーデータを投入する（本物の個人情報は使わない）
2. `pnpm dev` でローカル起動し、ヘルスチェックが 200 を返すまで待つ
3. 対象仕様（docs/specs/NNN-*/SPEC.md）の**受け入れ条件を 1 つずつ** E2E で確認する
   - `pnpm e2e` を Chromium（Android 想定）と WebKit（iPhone 想定）の両方で実行する
   - 画面の変更はスマホ幅でスクリーンショットを撮る
4. 不安定なテスト（実行ごとに結果が変わる）を見つけたら、再実行でごまかさず原因を直す

## 3. レビュー

1. `/code-review` を実行し、REVIEW.md の基準で Important が 0 件になるまで直す
2. `/security-review` を実行する
3. レビューの往復は最大 3 回。それでも解決しない指摘は、試したことを添えてひでに報告する

## 4. 証拠の報告（承認ポイント 2 の材料）

PR 本文に次を書く。**実行した手順と結果がない成功報告はしない。**

- 対応する仕様（docs/specs/NNN-*/SPEC.md へのリンク）
- 受け入れ条件ごとの結果（OK / NG と根拠）
- スクリーンショット（Chromium・WebKit）
- 実行したコマンドとテスト結果の要約
- リスク（要注意パスの変更、マイグレーションの有無）
- 元に戻す方法

マージはひでが行う。`gh pr merge` は実行しない。
